# DVRMC Portable

A portable differential motor controller development repository. Shared C++14
implements the register engine and two wheel-speed PID controllers; a separate
C++ host library configures and operates it through an ordered register transport.
Vitis HLS and SmartHLS entry points use the same core and testbench.

This is a tested control/driver foundation, not yet a board-ready motor drive.
The CPU bus bridge, real-time scheduler, encoder capture, PWM/bridge output,
physical fault input and device-specific CDC/clock/reset integration remain to be
implemented. Requested PWM/filter/current settings are defined in the ABI but
cannot affect physical hardware until those blocks exist. Do not connect the HLS
core directly to bridge pins. Physical board validation is outstanding.

## Build and run without FPGA tools

```
cmake -S . -B build -DDVRMC_SANITIZE=ON
cmake --build build -j2
ctest --test-dir build --output-on-failure
./build/simulate
```

The example uses two simple motor models with different loads. Its gains are
illustrative, not tuned parameters for a physical motor. All defaults start
with outputs disabled and PID/feedforward gains zero.

## Software and hardware boundaries

- `MotorProperties`: rated speed/voltage, encoder PPR, gearbox ratio, wheel radius,
  requested current limit and wiring signs. An explicit JGA25-370 preset uses
  6 V, 130 RPM, 11 PPR and 468/10 reduction; it requires a wheel-radius argument.
- `PidParameters`: Kp, Ki, Kd, feedforward, derivative filtering and output limits.
- `Calibration`: encoder resolution scale and independent forward/reverse PWM
  gains and breakaway offsets.
- `MotorConfig`: all per-motor register values, including timing, ramp, watchdog
  and speed-estimator settings. Its layout comes from `config_fields.def`.
- `MotorController`: stage configuration and commands, commit atomically, stop,
  keep alive and read coherent telemetry.
- `DifferentialDrive`: convert linear/angular velocity to coordinated wheel
  targets, scaling both together if either limit is exceeded.
- `RegisterIo`: ordered transport contract. `MappedIo` adapts an externally owned
  device-memory mapping with an explicitly supplied platform barrier; `ModelIo`
  runs the same register engine locally. Mapping, permissions and OS ownership
  belong to the board-specific driver, not this library.
- `Device`/`wheel_step`: synthesizable core with no vendor headers, heap or
  exceptions. Host floating-point conversion is outside the synthesizable path.

See [architecture](docs/architecture.md), [register protocol](docs/registers.md),
[parameter table](docs/parameters.md) and [calibration](docs/calibration.md).
The repository does not replace either existing DVRMC tree.

## FPGA tool flows

AMD (run from `platforms/vitis` with Vitis on PATH):

```
vitis-run --mode hls --csim --config hls_config.cfg --work_dir ../../work/vitis_csim
v++ --compile --mode hls --config hls_config.cfg --work_dir ../../work/vitis_synthesis
```

The example target is xc7z020clg400-1. Change the part and clock for the board.
`dvrmc_top` uses a transaction handshake; the scheduler must hold inputs until
accepted and capture return/output values when the operation completes. It is
not a ready-made AXI register peripheral. Every register transaction and tick
is a distinct invocation. Encoder capture must continue while it is busy.

Microchip (run from `platforms/smarthls` with the installed SmartHLS on PATH):

```
shls init
# Select the actual PolarFire SoC part and clock in generated config.tcl / IDE.
shls -a --user_makefile makefile.user sw
shls -a --user_makefile makefile.user hw
shls -a --user_makefile makefile.user cosim
```

Keep the provided `makefile.user`; use the Makefile/config generated by the
installed SmartHLS release. The top is marked with `#pragma HLS function top`.
Import generated RTL into Libero SmartDesign, with the target-specific shell.
SmartHLS 2026.1 software simulation, RTL generation and RTL co-simulation passed
for a representative PolarFire SoC target. See the [Ubuntu 24.04 container and
license setup](platforms/smarthls/container/README.md) for reproducible commands.

## Development

`python3 tools/generate_registers.py` refreshes the documented parameter table
and SystemVerilog parameter offsets from the same definition used by C++.
State is explicit per motor. Configuration updates are atomic across both
motors. No host transport traffic is required for each encoder transition.
The current build supports two motors (`motor_count`); changing hardware channel
count requires changing the scalar HLS adapter and regenerating/verifying RTL.
No remote repository, board bitstream or license selection is implied.

See [validation record](docs/validation.md) for the tested versions, timing
estimate, co-simulation result and remaining platform verification.
